Pi Agent Setup

Dynamic AAD pipelines

Static chains have been retired. The owner constructs each workflow from task topology, risk, model profile, selected skills, browser/audit needs, and dependencies.

1. Ownership route

DIRECT
One coherent action
One proof
No browser or delegation
SLICE
One coherent outcome
One working owner
One independent audit
ROOT
Multiple ownership/acceptance boundaries
Integrated root verdict
Difficulty selects model depth. Ownership topology selects Direct, Slice, or Root.

2. Slice flow

Terra/high slice owner
Inspect · implement · verify
Luna explorer
only bounded discovery
Sol implementer
only deep isolated work
Terra browser
always separate context
Terra/high auditor
one independent boundary audit

The owner remains accountable. Support agents produce evidence or implementation results but do not decide the slice done-state.

3. Root flow

Sol/high root owner
│
├── Terra/high or Sol/high working slice A
│   ├── optional Luna discovery
│   ├── separate browser when needed
│   └── independent slice audit
│
├── Terra/high or Sol/high working slice B
│   └── independent slice audit
│
└── integrate changes + root evidence
    └── root integration audit when required

One root request has one root owner. Slices are defined by ownership and acceptance, not by a desire to parallelize.

6. Artifacts and observability

.pi/aad/<task-id>/
├── task.md
├── discovery.md       # optional
├── implementation.md  # optional separate implementer
├── browser.md         # browser work
├── audit.md           # Slice/Root
├── slices/            # Root only
└── artifacts/

These files are ignored by git and optimized for humans and child handoffs. Pi-subagents remains the live source for lifecycle state, current tools, recent output, tokens, duration, and needs_attention. Agents add only semantic PI_PHASE changes.

7. Parallelism gate

Parallel execution requires all of the following:

  1. inputs and contracts are settled;
  2. dependencies are complete;
  3. mutable surfaces do not conflict;
  4. outputs are independently verifiable;
  5. failure is isolatable;
  6. integration is cheaper than sequential execution.

Browser contexts, worktrees, and model profiles remain explicit per delegated task.
